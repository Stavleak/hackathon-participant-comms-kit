# Приложение дежурного коммуникаций

Next.js отвечает за формы, Rust — за проверку структуры и правил работы. Запуск и конфигурация описаны в [README](../README.md). Это одна приватная локальная рабочая среда события; доступ и сохранение обслуживает сервер приложения. Размещайте её только в предусмотренном README окружении, с защищённым доступом. Пользователь вводит организационные данные, а не JSON.

## Рабочий маршрут

1. Добавьте каждого затронутого участника и сотрудника по внутреннему ID. Метка может быть командой или ролью; имя, телефон и email для работы приложения не требуются.
2. Примите вопрос, назначьте владельца, обещанное обновление и следующий шаг. Ответ можно сохранить как черновик. Статус «Ответ готов» требует непустого текста; фактическую правильность и полномочия подтверждает организатор.
3. Создайте черновик решения: тема, владелец, срок, следующий шаг, предполагаемая версия, аудитория и единый текст объявления. Укажите старое и новое условие, причину, действие, точную дату с зоной и резерв помощи.
4. После настоящего утверждения запишите, кто и в какой роли принял решение, и свидетельство из рабочего журнала. Приложение фиксирует время записи. Утверждённая версия уникальна; аудитория не может содержать неизвестные или повторяющиеся ID.
5. Скопируйте утверждённое объявление и самостоятельно разместите его в согласованных каналах. Кнопка копирования сохраняет только текст в буфер обмена; она не отправляет email или сообщения в чат.
6. Для каждого получателя отдельно сохраните наблюдаемый статус и ручное свидетельство. «Отправлено», «доставлено» и «подтвердил текст» различаются. Ни один статус автоматически не появляется после копирования объявления.
7. Назначьте действия для неподтвердивших. Закрыть проверку можно только после явного подтверждения всей зафиксированной аудитории. Rust повторно проверяет это условие при сохранении, поэтому отключённая кнопка не является единственной защитой.

Панель работы показывает нерешённые вопросы, просроченные сроки следующих шагов и количество подтверждений по каждому решению. Знаменатель — уникальные получатели выбранной аудитории, а не число всех регистраций и не число попыток отправки. Для пары решение–получатель сохраняется одна текущая отметка; повторная проверка заменяет её, не увеличивая знаменатель.

## Время, конфликты и учебные данные

Поле даты использует часовой пояс браузера, названный над рабочими формами. Сохранённые сроки имеют точный момент RFC3339. При ручном тексте объявления самостоятельно укажите нужную аудитории зону и UTC-смещение; интерфейс не исправляет текст правил автоматически.

После конфликта ревизий загрузите актуальные данные и повторите необходимое действие. Приложение не должно молча перезаписывать правки другого оператора. Проверьте незавершённые поля перед повтором.

Реальная рабочая среда начинает с пустых массивов. Учебный пример загружается только явным действием с подтверждением в пустую среду. Его имена, утверждение и свидетельство вымышлены; демо показывает неподтвердившего получателя и заблокированное закрытие.

## Практические ограничения

Это инструмент организатора одной рабочей среды. Нет отдельных аккаунтов участников, доставки сообщений, интеграции с регистрациями, технической проверки прочтения, настройки ролей утверждающих или автоматической публикации FAQ. Указанное имя утверждающего — запись оператора, а не подтверждение личности или полномочий. Проверяйте реальный список регистраций и сохраняйте основания решений.

Один текст объявления и одна языковая редакция хранятся у решения; перевод и равенство смысла проверяются организатором вне приложения. Приложение не определяет справедливость нового условия и не обеспечивает доступность внешнего канала. Частные обстоятельства не переносите в общий FAQ. Заполненные данные держите вне публичного GitHub.

Текущая отметка уведомления не является неизменяемым журналом всех попыток. Для полной истории используйте связанный рабочий журнал и [шаблоны](../templates/shift-handoff.md). После утверждения серверная проверка обновления запрещает менять текст, аудиторию, версию и основание утверждения прежнего решения. Новое изменение правил оформляйте новым решением и версией, чтобы ранее собранные подтверждения не считались подтверждением другого текста. Закрытое решение и его свидетельства неизменны.

Проверки домена покрывают отсутствие подтверждения, блокировку закрытия, уникальность ID и версии, обязательные свидетельства, ссылки на аудиторию, независимость знаменателя, просрочку и строгую структуру. Пройденный тест подтверждает правила данных; он не свидетельствует о реальной отправке сообщения.
